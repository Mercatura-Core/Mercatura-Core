## M7.2-A: audit and concrete findings

The coordinated audit covered complete CPU controller/lifecycle and Solo
provider code; worker limits; GPU discovery/budgets, CUDA/OpenCL host backends,
staged device arithmetic and 64-byte line synchronization; Qt MiningSession,
MiningPage and WalletController unload ordering; owned PQ destination persistence;
node template/submission/validation interfaces; native wallet/controller/GPU/Qt
unit tests, functional inventory, configuration and platform CI. An internal
scratch audit was recorded before edits.

| Severity | Root cause | Fix and regression evidence |
|---|---|---|
| Medium | Solo currency was only parent/IBD-based, so an earlier same-parent job could be paired with a later retained template/body | Retain the exact issued header/target/coinbase and validity token; revoke it before every refresh; replacement, forged-target/coinbase and old-job submission tests |
| Medium | Solo disabled Core cooldown, and IBD latches false after first completion | Public-chain cooldown plus explicit local `BlocksAheadOfTip` checks before/after assembly and at currency checks; real accepted header without its body pauses work, then body connection recovers it |
| Medium | Hashrate timestamp preceded blocking provider calls while counters were read afterward | Sample time after provider work; bounded stalled-submission regression verifies completed hashes are divided by all elapsed time |
| Medium | Unknown host RAM allowed only one CPU context but skipped aggregate GPU-verifier admission | Apply the conservative unknown-memory context budget to CPU plus GPU verification; multiple-device/combined rejection before allocation and single-GPU allowance tests |
| Low | Qt checked node shutdown only at Start and could enable Start without a wallet | Poll-triggered cancellation; missing-wallet button/status checks; node shutdown while hashing and declined-unlock/retry coverage |
| Coverage | Early native block acceptance lacked reward-to-spend qualification | Production provider/controller mines 102 real blocks; PQ reward credit/maturity/signing, fee/subsidy and commitments; independent normal RPC-node import |

These are focused fixes and test/diagnostic additions, not new mining modes,
wallet architecture, GUI navigation or pool accounting features. No concrete
consensus bypass, private-key exposure or unauthorized reward substitution was
found. Exact-template binding prevents the earlier mismatched-template failure
without altering how Core validates proof of work or payouts.

## M7.2-B: CPU, wallet and chain qualification

The actual native controller and Solo provider, using real `PoWHashContext`
hashing and normal `BlockTemplate::submitSolution`/Core consensus, produce the
qualification chain. A test-only bounded provider wrapper stops after the
requested accepted-block count; it changes neither targets nor validation.
One- and two-worker phases exercise persistent contexts and distinct nonce
allocation; the short two-worker fixture uses both CPUs explicitly, while the
production responsiveness reserve remains unchanged.

Evidence includes:

* Genesis/early-height block production, current parent, extranonce replacement,
  header/target/coinbase binding and normal difficulty checks.
* Correct wallet-owned witness-v2 PQ reward output, exact bootstrap SP-LT command
  plus transaction fees, and no positive diversion/mandatory-fee output.
* Depth 100 remains immature; depth 101 credits the first spendable reward.
  Ordinary coin selection excludes the immature reward. Explicit coin control
  can pre-sign it, but normal mempool admission rejects premature spending.
* A normal wallet-created ML-DSA-signed transaction spends the matured native
  coinbase; a subsequent controller-mined block includes it and credits a second
  owned PQ wallet. Merkle and witness commitments are explicitly checked.
* Every retained active-chain block is re-read, checked against its block index,
  rehashed through MercaHash and compared with expected subsidy/fees.
* A separate normal regtest RPC process accepts all 102 exported public blocks,
  checks height/reward address after each, verifies final fee/subsidy statistics
  and spend inclusion, and handles duplicate import without height change.
  No `generatetoaddress` substitutes for controller production in this gate.
* Real competing block arrival, stale solution rejection, invalidation/reorg,
  new-parent/replacement work and recovery. A small SHA256d block identifier
  with excessive MercaHash work digest is rejected by Core; the two hashes are
  not conflated.
* Public IBD, unavailable tip/template and interrupted template wait; no inbound
  peer requirement. Qt node shutdown, owner/unrelated wallet unload, reload,
  switching, destructor ordering, locked reuse, relocking and declined unlock.

The real qualification chain covers bootstrap heights, not 311,041 mined
blocks. Existing adaptive-emission/fixed-point/controller suites exercise the
later SP-LT rules deterministically; no adaptive consensus logic was changed.
Wallet restart/database persistence also receives native functional coverage.
The new producer uses a mock wallet database inside a real chain/node fixture;
the independent RPC node uses ordinary on-disk block/chainstate storage. This
is not evidence of a manually operated public-testnet or Windows wallet.

Machine: managed Debian 13 x86_64 KVM guest, AMD EPYC 9V74 model string,
three exposed logical CPUs, cgroup quota 200,000/100,000 (two CPU equivalents),
8 GiB memory limit, no swap. Compiler GCC 14.2.0, integrated Release `-O2` plus
repository hardening; Qt 6.8.2, SQLite 3.46.1. This is neither the owner's Ryzen
nor a tested Hostinger deployment. No energy/power measurement was available.

Sequential isolated measurements used the same integrated hardened Release
binary, after all local functional/build load ended. Each count ran three

Production detection recommends/permits one worker on this two-CPU quota. The
explicit two-worker benchmark uses the reserved CPU only in this isolated helper;
it is not a recommendation to starve the actual node/GUI. Scratchpads were exactly
128/256 MiB. All six cycles ended with zero active workers. Stop request times
were 0.010–0.021 ms; observed join times were 50.5–160.7 ms, bounded by completion
of the current frozen hash. These observed times are not worst-case guarantees.
Each cycle issued five jobs, including the initial job and four replacements.
Current RSS after stop was 2,256,896 bytes (one worker) or 2,269,184 bytes (two),
unchanged after the first cycle of each process; no retained scratchpad growth
was observed in this short check. This is not a long-duration leak/soak claim.

Measurement source: helper completed-work/steady-clock/`std::clock` counters,
Linux `/proc/self/status` and `getrusage(RUSAGE_SELF)`. Hash throughput includes
startup, coordinator and cleanup wall time. No wall-plug/package power data,
owner hardware, GPU or Hostinger throughput is inferred. Exact commands:

```sh
work/build/bin/mining-bench 1 10 3
work/build/bin/mining-bench 2 10 3
```


`mining-bench` is a test-build helper, never installed. It uses the production
controller and native hash factory against clearly synthetic public work and
no node/wallet. Jobs expire every two seconds to exercise refresh. Defaults use
production recommendation; explicit short experiments may use the reserved CPU,
identified in JSON, while retaining detected CPU and memory bounds. Duration is
1–60 seconds and cycles 1–10. It reports completed hashes/wall time, process CPU
time, request/join latency, refreshes, scratchpad bytes and Unix peak RSS. Linux
also reports current RSS before/after cycles; Windows needs an external working
set measurement. This does not measure a full-node workload or GPU performance.

## Known limitations, blockers and M7.3 prerequisites

* Physical NVIDIA/AMD hashing, Windows CUDA compilation/runtime, native owner
  Windows Qt operation and public-testnet discovery/payout/soak are outstanding.
  No VPS, WAN/TLS cohort, Hostinger CPU-credit or energy claim is made.
* Public-testnet discovery is probabilistic; a bounded run cannot promise a
  reward. Regtest production is the deterministic software qualification gate.
* Driver calls can hang despite cooperative cancellation; neither an asynchronous
  Stop nor current bounded launch design can forcibly preempt a failed driver.
  Normal current CPU hash and block processing can also delay final join.
* Active-tip acceptance observation can undercount an immediately extended block.
  Use chain/wallet records to confirm rewards. Diagnostic counters are session
  observations, not an independent full-chain ledger.
* Automatic CPU count is a conservative resource estimate, not measured hardware
  autotuning. cgroup v1 and Windows job-object limits remain undetected. System
  allocation/overcommit and background memory pressure still matter.
* The owned address-book marker may be renamed/deleted, requiring fresh derivation.
  A cached public destination allows locked mining; no private keys enter jobs,
  CPU/GPU workers or proof exports. No new unlock persistence is introduced.
* No manual long-duration soak, packaging installation on the owner's machine,
  physical driver-removal test or adaptive-era 311,041-block native chain was run.

Recommendation: close M7.2 as the automated software-qualification milestone.
All available required gates passed, and no unresolved software security or
correctness blocker was identified. Structured M7.3 manual testing can begin
with the prerequisites and outstanding hardware/public-testnet gates below.
This recommendation does not establish public-release or mainnet readiness.

The [M7.3 manual plan](M7.3-MANUAL-MINING-TEST-PLAN.md) supplies ordered build,
synchronization, owned PQ destination, CPU performance, start/stop/unload/reload,
reward/maturity/send, peer activity, diagnostics and bounded soak procedures with
practical runtime estimates. Real GPU and future KVM 2 coordinator/WAN work are
separate explicit gates. Existing KVM 2 3% baseline utilization and planned KVM 4
specifications are not treated as measured qualification evidence.
