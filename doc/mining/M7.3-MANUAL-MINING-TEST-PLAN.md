# M7.3 manual mining test plan

Use this plan after the automated M7.2 gates in
[M7.2 handoff](M7.2-SOLO-RELEASE-QUALIFICATION-HANDOFF.md) pass. This is a
qualification plan, not authorization to deploy a VPS, launch mainnet, merge a
protected branch, or change difficulty. Test only Mercatura public testnet or
isolated regtest. P2Pool and pool identity retirement remain deferred.

## Candidate and prerequisites

Repository: `https://github.com/Mercatura-Core/Mercatura-Core`.
Branch: `feature/qt-solo-release-qualification`.
Tested source SHA: `25a4d83bc53a8df214e412515c4c10c6795b0433` (final documentation-only HEAD is recorded
in the handoff checkpoint and delivery response). Pin that source SHA for builds;
record any packaging flag differences. Existing released binaries from M2/M5
are not evidence for this candidate. CI compile/test success does not establish
that an owner has a runnable packaged binary with every required dependency.

The owner has Windows 11 Pro, Ryzen 5 4600G and Ubuntu 22.04.6 under WSL2.
Check actual free RAM, compiler versions, disk space and drivers first. WSL
Linux execution is distinct from native Windows Qt execution. The planned RTX
5060 is not presently available; defer its runtime gate until real hardware is
available. Use GCC >=12.1, CMake >=3.22 and Qt >=6.2 per the repository dependency
policy; Ubuntu 22.04's default compiler may need upgrading. Follow
[Unix builds](../build-unix.md), [Windows MSVC builds](../build-windows-msvc.md)
and [GPU builds](../native-gpu-mining.md) for prerequisite installation. Do not
replace the owner's existing compiler/environment merely to start this plan.

## 1. Obtain and build the pinned candidate

In an existing clean checkout, fetch only the candidate branch and inspect
status. Preserve other worktrees, M6 work and uncommitted files. Use an additional
checkout/worktree rather than resetting existing work:

```sh
git status --short
git fetch origin refs/heads/feature/qt-solo-release-qualification
# Inspect FETCH_HEAD and the recorded source SHA before creating this worktree.
git worktree add --detach ../mercatura-m73 25a4d83bc53a8df214e412515c4c10c6795b0433
cd ../mercatura-m73
mkdir -p work/results
git rev-parse HEAD
```

WSL/Linux CPU-only build, after installing the documented dependencies:

```sh
cmake -S . -B work/build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_GUI=ON -DBUILD_TESTS=ON -DENABLE_IPC=OFF \
  -DWITH_ZMQ=OFF -DWITH_DBUS=OFF -DWITH_QRENCODE=OFF \
  -DWITH_CUDA_MINING=OFF -DWITH_OPENCL_MINING=OFF \
  -DMERCATURA_PUBLIC_TESTNET_RELEASE=OFF
cmake --build work/build -j4 --target bitcoin-qt bitcoind bitcoin-cli \
  test_bitcoin test_mining-qt test_poolclient-qt pool-native-test-client mining-bench
```

For native Windows CPU-only Qt, use Developer PowerShell for the supported
Visual Studio 2026 toolchain, with `VCPKG_ROOT` already configured. Estimated
runtime is in the table; do not start another dependency build concurrently:

```powershell
cmake -S . -B work/build-win --preset vs2026 `
  -DVCPKG_INSTALL_OPTIONS=--clean-after-build `
  -DVCPKG_MANIFEST_NO_DEFAULT_FEATURES=ON `
  '-DVCPKG_MANIFEST_FEATURES=qt;wallet;tests;pool-client-tests' `
  -DBUILD_GUI=ON -DBUILD_TESTS=ON -DENABLE_IPC=OFF `
  -DWITH_ZMQ=OFF -DWITH_DBUS=OFF -DWITH_QRENCODE=OFF `
  -DWITH_CUDA_MINING=OFF -DWITH_OPENCL_MINING=OFF `
  -DMERCATURA_PUBLIC_TESTNET_RELEASE=OFF
cmake --build work/build-win --config Release -j4 --target bitcoin-qt bitcoind bitcoin-cli test_bitcoin test_mining-qt test_poolclient-qt mining-bench
```

`vs2026-static` is a separate packaging gate. Use the supported `vs2022-gpu`
preset for CUDA 12.8 with VS2022 v143 14.40, as documented in the GPU guide;
do not assume the newer MSVC compiler is CUDA compatible. An OpenCL-enabled
build requires the AMD manifest feature and `WITH_OPENCL_MINING=ON`. A compiler
success without a selected real device remains a compile-only result.

On Windows, use `work/build-win/test/functional/test_runner.py` and
`work/build-win/bin/Release/test_bitcoin.exe`; use CTest for Qt so the required


Record exact passes/failures/skips. The GPU checker exit 77 means hardware was
unavailable; it is not a successful runtime test.

## 3. Start the full node and wallet on public testnet

Use an isolated data directory. Run Qt as the full node; do not simultaneously
run `mercaturad` against the same directory. The current documented bootstrap
peer is `node1.mercaturacore.com:27778`; confirm it still serves the intended
Mercatura public-testnet genesis before relying on it. No inbound-P2P rule is
required. Keep RPC on localhost using the ordinary cookie authentication.

Native Windows PowerShell, from the candidate checkout:

```powershell
New-Item -ItemType Directory -Force work/m73-testnet, work/results | Out-Null
$M73Data = (Resolve-Path work/m73-testnet).Path
$M73Bin = (Resolve-Path work/build-win/bin/Release).Path
& "$M73Bin/mercatura-qt.exe" -testnet "-datadir=$M73Data" -server -debug=validation -addnode=node1.mercaturacore.com:27778
# Run subsequent CLI queries from a second terminal with these two variables set.
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" getblockchaininfo
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" getnetworkinfo
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" getpeerinfo
```

Linux/WSL equivalent:

```sh
mkdir -p work/m73-testnet work/results
M73_DATA="$PWD/work/m73-testnet"
work/build/bin/mercatura-qt -testnet -datadir="$M73_DATA" -server \
  -debug=validation -addnode=node1.mercaturacore.com:27778
# Run CLI queries from another terminal after setting M73_DATA there.
work/build/bin/mercatura-cli -testnet -datadir="$M73_DATA" getblockchaininfo
work/build/bin/mercatura-cli -testnet -datadir="$M73_DATA" getpeerinfo
```

Wait for `initialblockdownload=false`, a connected active tip, and caught-up
headers. Verify `getblockhash 0` is
`b3fc707c9a89dc45d1cf6a837284b22ad2b6fd41b99af601079db9dcbeff6920`,
the pinned source public-testnet genesis, and compare with an independent
testnet reference. Public-testnet RPC port is 27775 and logs are under the
isolated directory's `testnet/debug.log`. Confirm at least one usable
peer and continuing validation/relay; outbound-only peers are sufficient.
Opening the wallet/Mining page must leave the worker count and hash count zero.
Create/load a test wallet named `m73-solo` through the normal Qt wallet UI.

## 4. Confirm the owned PQ destination and start CPU Solo

Open Mining, choose Solo Mining and CPU. Choose Automatic, then Start Mining.
For a newly encrypted wallet, accept the standard unlock dialog only to derive
its reward address. Confirm it relocks after preparation; an existing persisted
address must be reused while locked without another unlock prompt.

Copy the displayed public reward address into `$M73Address` in PowerShell and
check ownership (use the exact chosen wallet name):

```powershell
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" -rpcwallet=m73-solo getaddressinfo $M73Address
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" getmininginfo
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" -rpcwallet=m73-solo getbalances
```

Require `ismine=true`, witness version 2 and the public-testnet prefix `tmca1z`.
The wallet's `Mercatura mining reward` address-book entry must match the page.
An unsupported/classical/wrong-network destination fails the gate.
`getmininginfo.networkhashps` estimates the network, not this controller's local
hashrate. Use the page's completed hash count and measured local H/s for local
performance. An IBD/headers-ahead pause must show waiting rather than hashing.
Solo must work without a pool endpoint, external miner or second blockchain.

## 5. Compare worker efficiency and responsiveness

On the Ryzen, Automatic is a conservative resource estimate, not a promise that
it selects the fastest count. There is no global eight-worker cap. Compare
Automatic and allowed manual counts, initially 1, 4 and 8. If the actual detected
manual maximum allows it, compare 10/11 as well. The production CPU reserve can
exclude 12 on a 12-thread host; the bounded isolated benchmark below can measure
12 separately. The earlier owner observations (37 H/s at 8, 40–41 H/s at 12)
are historical machine-specific data, not measurements of this candidate.

With the node stopped, these three 60-second experiments take about 3 minutes:

```powershell
& "$M73Bin/mining-bench.exe" 4 20 3 > work/results/cpu-4.json
& "$M73Bin/mining-bench.exe" 8 20 3 > work/results/cpu-8.json
& "$M73Bin/mining-bench.exe" 12 20 3 > work/results/cpu-12.json
```

Counts are rejected if the detected CPU/memory benchmark budget cannot support
them. Explicit benchmark counts can use the CPU reserved in production; the
output identifies this. Do not run these experiments concurrently with the
node or other benchmarks. Windows benchmark RSS is not currently exported;
record peak working set/private bytes from Task Manager/Performance Monitor.
The Linux version reports process peak RSS via `getrusage`.

Then compare actual Qt mining with peers active for 5 minutes per allowed count.
Record H/s, completed hashes, CPU%, RAM, UI interaction latency and peer activity.
Prefer stable hashing with responsive wallet/network operation. Record measured
power only with its instrument/source (e.g. wall meter); TDP is not consumption.
No watt or energy-efficiency result is required without a suitable instrument.

## 6. Stop, restart and lifecycle checks

During hashing, click Stop. The UI must show stopping until workers actually
join; the current hash/driver call may finish. After confirmed stop require zero
active workers, zero current rate and no increasing hashes. Record stop latency.
Repeat 10 start/stop cycles, including one immediate stop during preparation.

Switch wallets while running: a second wallet must not start a competing fleet.
Unload the owning wallet, then reload it and restart. Check cleanup before model
removal, owned address reuse and a fresh session. Unloading an unrelated wallet
must leave mining intact. Close Qt while hashing, reopen the same test directory,
and confirm mining remains stopped until Start is pressed. Test declined unlock,
missing wallet, failed GPU selection and return to CPU; statuses must be honest.
For network recovery, briefly disable network activity only on this test node,
restore it, and verify peers/tip catch-up and mining recovery. Do not infer a
valid remote tip merely from a network-activity toggle or a stale recent tip.

## 7. Verify discoveries, reward ownership and maturity

Regtest discovery is deterministic enough for the automated gate. Public-testnet
Solo discovery is probabilistic: mean time is approximately
`150 seconds * network H/s / local H/s`, and there is no guaranteed block within
30 minutes or 2 hours. No discovery is not itself a controller failure.
Never modify public network PoW/difficulty or use regtest blocks on testnet.

If a block is discovered, record the page counters/status, block hash/height,
`getblock <hash> 2`, wallet `gettransaction <coinbase-txid>` and `getbalances`.
PowerShell commands for a discovered block (`$M73Block` is its recorded hash):

```powershell
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" getblock $M73Block 2
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" -rpcwallet=m73-solo gettransaction $M73Coinbase
& "$M73Bin/mercatura-cli.exe" -testnet "-datadir=$M73Data" -rpcwallet=m73-solo getbalances
```

Verify the active chain, native PQ reward script, correct subsidy plus fees,
zero diversion outputs, merkle/witness commitment and wallet ownership.
Processing is not acceptance; the accepted counter observes the exact active tip
and can miss a block that a peer immediately extends. Independently inspect the
chain and wallet; a stale/rejected solution must not be called a reward.

Coinbase has depth-101 wallet spendability with the existing 100-block maturity
rule. At 150 seconds/block, 100 further blocks average about 4 hours 10 minutes,
with actual network progress variable. Verify immature/trusted balances at the
boundary. After maturity, send a small testnet amount (e.g. 1.00 MCA) to a second
owned test wallet through Send; verify ML-DSA PQ authorization, confirmation,
fee accounting and receiver credit. Do not demand a same-day reward/maturity
result when no block has been discovered.

## 8. Real GPU gate, when hardware is available

Record GPU model, driver, CUDA/OpenCL runtime, compiler, selected device IDs,
context count, memory and OS. Execute `mercatura-gpu-check --list`, then the
checker against the actual selected device as described in the GPU guide.
For the documented supported VS2022/CUDA toolchain, a concrete optional
build/check sequence is:

```powershell
cmake --preset vs2022-gpu -DENABLE_IPC=OFF -DWITH_DBUS=OFF -DWITH_QRENCODE=OFF -DMERCATURA_PUBLIC_TESTNET_RELEASE=OFF
cmake --build work/vs2022-gpu --config Release -j4 --target bitcoin-qt mercatura-gpu-check
$M73GPU = (Resolve-Path work/vs2022-gpu/bin/Release).Path
& "$M73GPU/mercatura-gpu-check.exe" --list
# Set M73Device to an actually discovered supported ID, for example cuda:0.
& "$M73GPU/mercatura-gpu-check.exe" $M73Device
```

The initial build may take 1–4 hours with cold dependencies; allow 5–15 minutes
for the first real-device check, then record its actual duration. Launch that
GPU-enabled Qt binary against the same isolated testnet directory only after
closing the CPU-only Qt process. Permanent vectors must pass on that device
before any runtime success claim.
Use one context and the default 10 ms yield first, then a bounded context count.

Test GPU-only and CPU+GPU Solo, correct CPU-verified candidate handoff, Stop,
restart and recoverable initialization failure. Test multiple devices if present.
Never physically remove a GPU while it hashes as a fault test. Use controlled
unavailability/restart, and capture driver errors if they occur naturally.
Do not claim bounded cancellation of a hung driver; cancellation is cooperative
between driver calls. Repeat CPU-only builds and conventional Pool regression
when changing GPU packaging. No compatible GPU/exit 77 is an outstanding gate.

## 9. Bounded soak and results package

After the interactive gates, run a 30-minute public-testnet CPU soak with normal
wallet send/receive and peer activity. Sample once per minute, not in a tight RPC
loop. Check steady memory, plausible completed-work H/s, fresh work, counters,
peer responsiveness, no unlock persistence, and clean stop/restart. Review results
before a 2-hour follow-up. Larger stress or a multi-day soak needs an explicit
schedule and resource budget in M7.3.

Collect into `work/results/`: candidate SHA/build flags; OS/CPU/RAM/driver data;
exact test pass/fail/skip totals; benchmark JSON; time-series memory/CPU/H/s and
stop latencies; public node/peer snapshots; public destination/coinbase/block/tx
IDs; relevant debug.log excerpts; and screenshots of status/errors if needed.
Include observations with no discovery and every unexpected result. Do not
include wallet seed, passphrase, private-key material, cookies or wallet files
in the shared diagnostics package. Backups remain in the owner's own custody.

M7.3 additionally coordinates the future KVM 2 testnet M3/Explorer deployment,
WAN/TLS pool operation, small miner cohort, PQ payouts and Hostinger resource/
CPU-credit measurements. The previously reported 3% baseline load is not a
qualified profile. KVM 4 mainnet/Explorer/pool and KVM 8 are plans, not measured
deployments. Use the M7.1 handoff and operator docs for that separately reviewed
work. M7.2 has performed no VPS deployment.

Close M7.3 only with explicit real Windows Qt, public-testnet and applicable
hardware/packaging outcomes. A compile, mock, or regtest success alone does not
establish public-release readiness.
